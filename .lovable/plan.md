# Sync with your external builder, then get a final ZIP back

You have work sitting outside (in your local/agent copy) that was never pushed, and meanwhile this Lovable project moved forward. The safe order is: push Lovable's current state to GitHub first, then hand your builder a prompt that makes it diff its copy against the repo instead of overwriting it.

## Step 1 — Push this project to GitHub

Use the GitHub button in the top right of the editor (Connect / Sync). Once synced, every change here lands on the repo automatically, and your builder can pull the true current state.

## Step 2 — Give your builder the prompt below

Copy this whole block to your external coding agent.

```text
The Lovable repo has been updated. Do NOT overwrite it with your local copy.

TASK
1. Pull the latest main from the GitHub repository.
2. Diff it against the work you had staged but never pushed. For every file that
   differs, decide per file: keep repo version, keep yours, or merge. Never bulk-replace.
3. Apply your remaining work on top, then deliver a single ZIP of the full project
   ready to push back, plus a CHANGES.md listing every file you added, edited or deleted
   and why.

STACK — do not change any of this
- TanStack Start v1 (React 19, Vite 7). File routes in src/routes. Never edit src/routeTree.gen.ts.
- No react-router-dom, no src/pages, no src/App.tsx, no BrowserRouter.
- Server logic = createServerFn from '@tanstack/react-start'. Public/webhook endpoints =
  file routes under src/routes/api/public/*. No Supabase Edge Functions.
- Tailwind v4 via src/styles.css (@theme tokens). No tailwind.config.js. No hardcoded
  colours in components — use the semantic tokens already defined.
- Runtime is a Cloudflare Worker: no child_process, sharp, canvas, puppeteer, fs.watch.

DO NOT TOUCH (auto-generated by Lovable, will be regenerated and your edits lost)
src/integrations/supabase/client.ts, client.server.ts, auth-middleware.ts,
auth-attacher.ts, previewAuthStorage.ts, types.ts, src/routeTree.gen.ts, .env,
supabase/config.toml.
Schema changes must be new SQL migration files only — never hand-edit types.ts.

CURRENT DATABASE (public schema, all RLS-enabled)
profiles, user_roles, courses, lessons, enrollments, course_pricing,
academy_submissions, pm_review_access, projects, tasks, talent_profiles,
talent_earnings, payout_requests, invoices, escrow_status, audit_logs.
Rules that must survive:
- Roles live ONLY in user_roles. Never store a role on profiles. Signup trigger forces
  'client' or 'student'; role can only be changed by an admin.
- Every new public table needs GRANTs (authenticated + service_role; anon only if a
  policy allows anon reads), then ENABLE ROW LEVEL SECURITY, then policies.
- Lesson content / project briefs readable only by a student actively enrolled in that
  course, or an admin. No anon read on invite/token/payment/role tables.
- No dummy or seed rows unless a screen is specified to ship with demo data.

WHAT ALREADY EXISTS IN THE REPO (don't rebuild)
- Public pages with their own SEO head(): /, /agency, /academy, /about, /contact,
  /terms, /privacy, /login, /signup, /talent-application, /invite/$token.
- Design system in src/styles.css: Space Grotesk display + Inter body, electric-blue
  accent on white, sticky blurred header, compact two-column mobile footer,
  scroll-reveal via src/components/Reveal.tsx.
- Auth: src/lib/auth.tsx (role-aware redirects), src/components/RequireRole.tsx,
  _authenticated pathless layout with ssr:false.
- Floating AI support chat: src/components/SupportChat.tsx mounted in __root.tsx,
  streaming endpoint src/routes/api/public/support-chat.ts, grounded in
  src/lib/chat-brief.ts (Lovable AI Gateway, rate-limited). Keep it grounded — it must
  never invent prices, clients or stats.
- Portals: admin / client / pm / talent have first-pass content; student portal is still
  an empty shell.

WHAT IS STILL MISSING — build these
1. Student portal (currently empty): enrolled courses, linear lesson player with YouTube
   progress tracking, sequential unlocking, exam + project submission, certificate state.
2. Academy AI flow: AI-generated per-student exams and project briefs so no two students
   get the same paper; AI verdict written to academy_submissions; Director/Admin
   certification queue; PM review only when pm_review_access.enabled is true.
3. Course Editor for admins: full CRUD on courses, lessons, learning_objectives,
   project_theme, cover_image_url, school, and per-region pricing (NG / AF / GLOBAL).
4. Admin portal for real: user list + role changes (writing to user_roles + audit_logs),
   talent application review, PM invites, payout approvals, audit log view.
5. Client portal: project status, invoices, escrow state, message-PM path.
6. Talent portal: assigned tasks, earnings, payout requests wired to real tables.
7. Contact form must actually persist and notify (sender domain notify.ndh.com.ng).
8. Branded auth emails: confirmation, password reset, invite.
9. Refunds / commitment-terms page linked from the footer, plus a trust page.
10. sitemap.xml, robots already exists, analytics hook, absolute og:image per key page.
11. Styled 404 and error states consistent with the design system.

QUALITY BAR — apply your own judgement beyond the list
- Content honesty: no fake testimonials, fake clients, fake team, fake stats, no
  "Sokoto to the world" style origin copy. Talent stays anonymous (IDs like NDH-DS-1234),
  no personal photos.
- Tone and layout should read like Upwork / Toptal: mature, neutral, global.
- Accessibility: real headings hierarchy (one H1 per page), alt text, focus states,
  keyboard-usable menus and dialogs.
- Performance: lazy-load below-the-fold images, no oversized assets.
- Mobile: verify every page at 360px width.
- Security: no service-role key in client code, validate all server-fn input with zod,
  verify caller before any privileged read/write.

BEFORE YOU ZIP
- `bun install` clean, typecheck clean, production build succeeds.
- Every route linked in the nav/footer actually resolves.
- Every content route has a unique title + description + og tags.
- Include CHANGES.md and any new SQL migrations under supabase/migrations/.
```

## Step 3 — When the ZIP comes back

Push it to the same GitHub branch; it syncs into Lovable automatically. Then I run a build check, a security scan, and a mobile pass on every page before publishing.

Nothing in this project is being changed by this plan — it only produces the sync instructions. Say the word if you'd rather I keep building the missing portals here instead of handing them to the external builder.
